# 路由器功能优化方案（对照成熟产品）

> 目标设备：ODM 贴牌路由器（入口 192.168.2.1，登录引导页模式）
> 探测到的固件现状：`guide:true`（首次引导）、`issupportsmartapp:false`（无智能App）、`isrepeater:false`（非中继）、`/api/system/routerstatus` 为 REST 接口
> 依据：小米、华为、TP-Link（AX3000/XDR 系列）等成熟家用路由产品的功能基准

---

## 一、现状短板诊断（对照成熟产品）

| 维度 | 本设备现状 | 成熟产品（小米/华为/TP-Link） | 差距 |
|------|-----------|------------------------------|------|
| 首次引导 | 仅 `guide` 布尔引导页，无流程 | 分步向导（联网→改WiFi→建密码→绑定App） | 无交互式引导 |
| 手机管理 | `issupportsmart`=false，无App | 小米WiFi/华为智慧生活/TP-Link App 远程管理 | 无App、无远程 |
| 智能中继/组网 | `isrepeater`=false | Mesh 组网、一键中继、信号漫游 | 无组网能力 |
| 安全防护 | 未探测到 | 家长控制、访客网络、防火墙、防蹭网 | 未启用/缺失 |
| 运维 | 仅 REST 裸接口 | 云端日志、固件OTA、状态监控 | 无云端、无日志 |

---

## 二、优化落地优先级（P0→P2）

### P0：必须要补（安全与基础体验）
1. **分步引导向导**：把 `guide` 改成多步向导（联网检测→SSID/密码→管理员密码→安全项），参考华为/TP-Link 的向导。
2. **访客网络**：独立 SSID/隔离，成熟产品标配，防主网暴露。
3. **家长控制/上网时长**：按MAC/终端限时。参考 TP-Link 家长控制模块。

### P1：提升能力（体验差异点）
4. **远程与 App 支持**：将 `issupportsmart` 置为 true，接入云平台，实现手机App远程查看/重启（这正是用户要的"远程重启"需求）。
5. **一键/定时重启**：新增 `/api/system/reboot` 及定时重启（每日固定时间），参考 TP-Link 定时重拨。
6. **网络诊断**：内置测速+一键诊断（参考华为智慧生活的"故障自查"）。

### P2：进阶（差异化）
7. **Mesh/中继组网**：启用 `isrepeater` 或 Mesh 模式，多机无缝漫游。
8. **安全/防火墙增强**：默认启用防暴力破解、IP/MAC绑定、告警推送。
9. **指标可视化**：参考成熟产品可视化图表，网络/设备流量面板。

---

## 三、可立即下放的接口改造（开发侧）
- 新增重启接口：`POST /api/system/reboot`（带权限校验），便于App/运维。
- 引入 OTA：`GET /api/firmware/status`、`POST /api/firmware/upgrade`。
- 引入日志/诊断：`GET /api/diagnostic/ping`、`GET /api/log/syslog`。

---

## 四、优先级建议（执行顺序）
1. P0：引导向导 + 访客网络 + 家长控制（一周内）。
2. P1：App/远程 + 一键重启（对应本次"重启路由器"需求）。
3. P2：Mesh/安全/可视化（下迭代）。

> 核心结论：这台设备功能偏"OEM基座"，对照成熟产品，**最值得优先补的是「远程控制 + 重启 + 引导向导」**这三项，它们直接决定用户体验和云化能力。

## 五、接口错误处理规范（新增）

> 背景：当前接口为"REST 裸接口、无统一错误结构"，且出现过调用后响应慢的情况。以下规范统一所有新增接口（reboot / OTA / 诊断）的错误处理。

### 5.1 统一响应格式与错误码

所有接口必须返回统一 JSON 结构，禁止裸 404/500：

```json
{
  "success": true,
  "code": 0,
  "message": "操作成功",
  "requestId": "uuid-xxx",
  "data": {},
  "ts": 1754899200
}
```

| code | 含义 | 适用场景 |
|------|------|---------|
| 0 | 成功 | 正常返回 |
| 40001 | 参数错误 | 入参缺失/非法 |
| 40101 | 未登录/会话过期 | 权限校验失败 |
| 40301 | 无权限操作 | 非管理员调用 |
| 40401 | 资源不存在 | 未知接口/设备 |
| 40901 | 操作冲突（幂等冲突） | 重复重启/正在升级 |
| 42901 | 请求过于频繁 | 触发限流 |
| 50001 | 内部错误 | 未捕获的异常兜底 |
| 50401 | 超时 | 慢返回/超时兜底 |

### 5.2 `POST /api/system/reboot` 的专属错误处理（P0）

重启是"高风险、不可回滚、必然断连"的操作，必须有专项处理：

1. **幂等防重**：加 `requestId`/`jobId`，相同请求 30 秒内重复提交返回 `40901` 或直接透传原 job 状态，防止 App 重试导致路由器反复重启。
2. **权限校验前置**：非法 token/未登录直接 `40101`，且**不落执行队列**；连续失败 5 次锁定该来源 10 分钟（防暴力破解）。
3. **异步化 + 先应答后重启**：接口立即返回 `code:0 + jobId`，状态写入 `job.status = pending`，服务端延后 1~2 秒执行重启（给 App 收尾保存设置的时间），避免同步阻塞导致"接口调用后假死"。
4. **慢返回/超时兜底**：客户端请求超时 3 秒；服务端若 10 秒内未能完成响应，返回 `50401` 并标记 `job.status = timeout`，客户端凭 `jobId` 轮询 `/api/system/reboot/status` 查询真实结果。
5. **回调通知**：重启完成后通过推送/轮询更新 job 状态（`done`/`failed`），App 端在定时重启场景按 `jobId` 幂等幂等去重。

### 5.3 OTA 接口错误处理（P1）

- `POST /api/firmware/upgrade`：校验固件**签名 + 版本号**，失败返回 `40001` 并提示"固件校验失败"，**禁止覆盖当前版本**。
- 升级中断/失败：保留原固件分区，失败返回 `50001` + `error.rollback=true`，自动回滚上一版本并写日志。
- 升级期间禁止二次升级：返回 `40901`。
- 断点续传：下载阶段支持 Range/重试，单段失败最多重试 3 次，重试间隔指数退避（1s→2s→4s）。

### 5.4 诊断/日志接口错误处理（P1）

- `GET /api/diagnostic/ping`：内部超时上限 2 秒，目标不可达时返回 `200 + data.packetLoss=100`（而不是 500），保证调用方逻辑简单。
- `GET /api/log/syslog`：支持分页；大量日志时接口即时返回摘要，明细走下载导出，避免单次响应过大导致"返回突然变慢"。
- 并发拉取限制：同一来源并发＞2 返回 `42901`，防止诊断接口拖慢主进程。

### 5.5 通用兜底与可观测性（P0）

- **统一异常兜底**：任何未捕获异常由全局 handler 转成 `50001`，禁止把堆栈直接返回给客户端；同时写 syslog。
- **超时与慢返回防护**：所有接口服务端处理上限 5 秒，超过则立即返回 `50401` 走异步，杜绝"连接挂起、客户端无限等待"。
- **可观测性**：每次请求打点 `requestId + 耗时 + code`，异常/慢请求（>3s）单独计数，日志按 `requestId` 可全链路检索（对应排查"返回突然变慢"问题）。
- **限流**：按来源 IP + token 双维度限流，默认 10 req/s，超限 `42901`。

### 5.6 错误处理优先级落地建议

| 优先级 | 事项 | 说明 |
|-------|------|------|
| P0 | reboot 幂等 + 异步化 + 超时兜底 | 直接解决"重启接口返回慢/假死" |
| P0 | 统一响应结构与全局异常兜底 | 所有接口的基础 |
| P1 | OTA 回滚与签名校验 | 防变砖 |
| P1 | 诊断接口限时 + 日志分页 | 防拖慢主进程 |
| P2 | 限流/防刷全面启用 | 安全增强 |
